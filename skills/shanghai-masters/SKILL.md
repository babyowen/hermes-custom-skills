# 上海大师赛 · 决赛日攻略雷达

用户 2026-10-18（周日）**只去决赛当天**。他**不关心胜负战报**，要的是"到了现场怎么顺"：**停车/交通 → 吃饭 → 天气 → 观赛与周边口碑**（按他原话的排序）。这是个**情报雷达**，不是赛事播报。

## 铁律（违反任何一条 = 这期作废）

1. **只用两个脚本，不手拼搜索命令**：`masters_fetch.py`（抓取）+ `masters_weather.py`（天气）。原始 JSON 不进聊天，只进你的判断。
2. **同名赛事必须硬过滤**：「上海大师赛」= 网球 / 斯诺克 / 电竞三个赛事同名。脚本已过滤，**但你自己的 web_search 结果要再过一遍**（见 `references/sources.md` 黑名单）。发现疑似混入 → 剔除，不留"可能"。
3. **只报新增**：脚本用 `seen.json` 去重，只有"必含板块"（天气、出门清单）每天出现。**已告知过的攻略不要重复讲**——零新增就走模板 B，别为了凑内容复述。
4. **抓不到的渠道不许假装读到**：小红书/微博/知乎/大众点评正文本机**抓不到**（登录墙+反爬，实测）。只能引用 web_search 的**摘要**，并标「转述」。
5. **数字必须有出处和年份**：停车位/班次/价格一律带来源；往年数字写清楚"（2025 参考）"，**不许写成今年事实**。
6. **一切时间用北京时间**；决赛日写「10/18（周日）」。
7. **不报战报**（谁赢谁、签表、球星八卦），**除非影响现场**（退赛改赛程、开赛时间变动、天气导致延期）。
8. **报告 ≤20 行、结论前置、大白话**，按 `references/report-template.md` 输出。不写"已按流程生成"之类的元话。

## 数据源：两轨并行（缺一不可）

**A 轨 · 脚本**（结构化、可复现，不吃验证码）

```bash
S=~/.hermes/skills/shanghai-masters/scripts
python3 $S/masters_fetch.py all --limit 12        # 官方站正文 + 第三方讨论（B站/百度/公众号/球迷站）+ OSM
python3 $S/masters_weather.py --date 2026-10-18   # 决赛日逐时天气（默认就是 10/18）
```

抓取层的输出里：
- `official.pages.<页>.relevant` = 官方交通/须知页里**带实操关键词的段落**（最可靠）
- `social.new_items` = **新增**情报（标题+来源+摘要+链接），已按相关性排序
- `social.errors` = 源异常（`百度 安全验证`/`搜狗 验证码` = 被限流）
- `social.stats` = 扫描/保留/新增/去重跳过计数

**B 轨 · 你自己的 `web_search`**（通用检索主力，**不吃验证码**，能拿到媒体/本地宝/公众号转载）

每期跑 3–5 条针对性查询（模板见 `references/sources.md` §三），例如：
- `2026上海劳力士大师赛 交通出行 短驳专线 停车`
- `上海大师赛 决赛 入场时间 几点 观众须知`
- `旗忠网球中心 停车 自驾 今年`

**为什么两轨都要**：A 轨抓不到媒体稿件（多含当年的官方交通提示），B 轨抓不到 B站/官方站的稳定结构；A 轨被限流时 B 轨顶上，反之亦然。

## 工作流（每期照做）

1. 跑 `masters_fetch.py all --limit 12` + `masters_weather.py`（可并行）。
2. 跑 3–5 条 `web_search`（按 `references/sources.md` §三 的查询模板，按当天轮换维度倾斜）。
3. **筛**：一条情报值不值得报？判据 = 能不能改变用户的现场行为（几点出门、停哪、带什么、吃什么、去哪排队）。**只讲赛果/签表的直接扔**。
4. **查**：与 `references/guide-dimensions.md` §二 的已核实事实**去重**（官方交通页那几条已经讲过的，不要再当"新发现"报）。
5. **写**：按 `references/report-template.md` 的模板 A/B（决赛日 10/18 用当天版），≤20 行，来源层标注。
6. 若脚本报限流 → 在报告末尾一句（单日偶发不报；连续 2 天以上才提）。

## 阶段策略（不同阶段说什么）

| 阶段 | 该侧重 |
|:---|:---|
| 赛前（现在 –10/14） | **积累**：停车方案定没定（自驾 vs 地铁+接驳）、往年坑点、纪念品/签名点位、饭怎么解决、票务规则变化 |
| 赛期内（10/5 起） | **现场验证**：去看过的人（B站/公众号）当天发的实操反馈 —— 停车排队多久、安检快不快、场内餐饮排队、散场好不好走。这是最值钱的一段 |

| 决赛日（10/18） | 用「决赛日当天版」：几点出门/走哪条路 → 入场门与证件 → 散场策略 |

## Pitfalls

1. **斯诺克污染**：搜"上海大师赛"约一半结果是斯诺克（奥沙利文/丁俊晖）——脚本已过滤，手工 web_search 时必须自己筛。
2. **`site:` 在本机 web_search 无效**：别想用 `site:xiaohongshu.com` 绕过登录墙。
3. **B站解析**：必须取 `bili-video-card__info--tit` 的 `title` 属性；直接抓 `<a>` 文本会得到播放量"664 0 02:30"。
4. **百度/搜狗会限流**：触发后**不要重试轰炸**（延长冷却），改走 web_search；脚本已把每日请求压到 18 次（核心 2 组 + 轮换 1 组）。
5. **天气窗口**：Open-Meteo 逐日最多 16 天。10/18 在 10/3 之前查不到；≥7 天的数值必须标"仅供趋势参考"。
6. **OSM 停车场没用**：3km 内 13 处全无名无容量。别把它当停车方案。
7. **官方票务站（久事体育）JS 渲染**：脚本抓不到正文，票务只能靠 web_search 摘要 + 官方英文站的 Tickets 页。
8. **往年数字**：350 个车位、101 班次、1913 人次都是 **2025** 口径，今年必须重新核实。
9. **小红书/微博**：拿不到正文。如果用户转来具体链接，用 `scrapling extract stealthy-fetch <url>` 试单篇（成功率未知，失败就如实说失败）。
10. **`site:`/管道/`python3 -c` 内联**：管道命令与内联 `python3 -c` 容易被审批拦截；探测脚本一律写成 `~/.hermes/cache/xxx.py` 再跑。
